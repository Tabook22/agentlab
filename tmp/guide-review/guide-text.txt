010 Introduction
011 This practical guide helps final year students build an assistant that suggests the identity of selected Omani plants from photographs. It explains the complete process in simple English, from collecting verified data to fine tuning Qwen3 VL 2B Instruct with Unsloth on a RunPod GPU Pod, evaluating the results, and preparing an application.
012 Students do not need to purchase a GPU server to complete the cloud prototype. A future local deployment requires suitable hardware and its own performance tests. The main academic task is to demonstrate whether training improves recognition using independent test photographs.

Complete the data checks before renting a GPU, run a short training test before a longer session, and save evidence at every milestone. 075 1 Understand the system and its limits
076 1 1 What you are building
077 A large language model or LLM primarily processes language. A vision language model or VLM processes images and language. Your photo recognition project therefore needs a VLM or a separate image recognition model. The text only Qwen2.5 7B and Llama 3.1 8B models cannot accept photos merely because you train them on plant descriptions.
078 You will adapt an existing VLM rather than create a foundation model from zero. In this guide, starting model means the pretrained model you adapt. An instruction tuned starting model already follows conversational instructions. A raw base model may require additional instruction training.
079 1.2 Where each part runs
080 
081 Cloud training and cloud inference are different activities. Training changes model parameters. Inference uses the finished model to answer a request. Use a Pod for training. Serverless is optional for serving requests after the model works.
082 1.3 What specialization can and cannot do
083 Fine tuning may improve recognition of the selected species and produce more consistent answers. It does not guarantee correct identification, exhaustive factual memory, or calibrated confidence. Closely related plants may require flowers, fruit, location, or specialist examination.
084 The app should return a suggested identity, visible features, limitations, and a request for additional photographs when needed. Never present a generated confidence percentage as a measured probability. Do not infer edibility or medicinal safety from the photo.
085 Checkpoint: explain to your supervisor why your project uses a VLM and what counts as a successful identification.

096 2 Plan the project and resources
097 2 1 Define a manageable scope
098 Begin by selecting 10 to 20 Omani plant species with help from a botanical adviser or plant specialist. Choose species for which you can collect photographs with verified identifications. Include photographs of different individual plants, taken from different angles and under different lighting and background conditions. Where possible, capture the whole plant as well as its leaves, flowers, fruits, or bark.
099 Include some visually similar species to test whether the model can distinguish between plants that look alike. Keep the project’s scope realistic: a model trained on a small selection of species should be evaluated on those species, rather than presented as capable of recognizing every plant in Oman.
100 For this project, students will fine-tune Qwen3-VL-2B-Instruct, an existing open-weight vision-language model (VLM) that accepts images and text. The original model already has general image-understanding abilities. Fine-tuning uses verified plant photographs and answers to adapt it to the selected Omani species.
101 The training method is QLoRA, which stands for Quantized Low-Rank Adaptation. QLoRA reduces training memory requirements by loading the original model in a compressed numerical form and training small additional parameters called adapters, while keeping the original model’s main weights frozen. QLoRA is the training method; the resulting system is called a fine-tuned VLM.
102 The research question is:
103 Does fine-tuning Qwen3-VL-2B-Instruct using QLoRA improve its ability to identify selected Omani plant species in new photographs, compared with the same model before fine-tuning?
104 In simple words: Does teaching the model with our plant photographs help it recognize plants more accurately in photographs it has never seen before?
105 To answer this question fairly, test both versions—the original model and the model with the trained adapter  on the same photographs excluded from training. These should show different individual plants from those used in training. Keep the prompts, image processing, and other test settings consistent. Compare the results to determine whether fine-tuning improved identification, which species remain difficult, and when the model should request another photograph instead of guessing.

The 2B size is a practical starting candidate for a student experiment; its suitability for Omani plants must be measured.

124 https://huggingface.co/Qwen/Qwen3-VL-2B-Instruct

126 3 2 Which files to use
127 Use a supported Hugging Face Transformers checkpoint or the matching Unsloth training checkpoint. Keep its processor, tokenizer, configuration, and chat template together. The processor prepares images as well as text.
128 A GGUF intended for an inference engine is not the starting checkpoint for the Unsloth training workflow in this guide. Export to a compatible deployment format only after training and checking vision support.
129 3 3 Record the exact experiment
130 Keep the repository ID, resolved model commit or revision, download date, package versions, GPU type, and image preprocessing settings. Model names alone do not fully reproduce an experiment. For the final run, use a pinned revision or a downloaded snapshot whose identity is recorded.
131 A free model means its weights can be obtained under its license. It does not mean free GPU rental, free storage, or free hosted API calls. Model licenses and your photograph or document permissions are separate matters.
132 3 4 A useful comparison
133 If time allows, compare the VLM with a conventional image classifier trained on the same species and split. A smaller classifier may be cheaper to run. Use the same test images and disclose differences in training data; do not assume the VLM must win.

136 4 Collect reliable plant photographs
137 4 1 Build a species catalogue first
138 Assign each species a stable ID such as OM001. Maintain an accepted scientific name, family, verified local names, synonyms, and supporting references. A local name may refer to more than one species. The catalogue should preserve this ambiguity rather than silently merge plants.
139 A botanist or qualified adviser should verify labels. Uncertain labels belong in a review queue. A model prediction or an internet filename is not sufficient ground truth.
140 4 2 Photograph diversity matters
141 Collect whole plant, leaf, flower, fruit, and bark views where appropriate. Include different individual plants, locations, seasons, lighting, distances, cameras, and backgrounds. Keep contextual metadata, but do not put exact sensitive locations into a public app.
142 As an initial collection target, consider 50 to 100 independent photographs per species from many individual plants. This is an illustrative pilot target, not an established minimum or a guarantee of success. More duplicate images of the same plant cannot replace independent examples.
143 Do not photograph one species only against a classroom wall and another only outdoors. The model may learn the backgrounds. Avoid name labels, watermarks that reveal species, or captions inside the training image that give away the answer.
144 4 3 Include difficult and unsupported cases
145 Add examples with blur, missing identifying parts, multiple plants, and species outside your supported list. Label genuinely ambiguous cases as uncertain. Unsupported species must not be forced into one of the known labels.
146 Do not use generated plant images as ground truth for scientific identification. Keep rights and attribution records for every external image. A picture on a public website is not automatically available for training or redistribution.
147 4 4 Quality review checklist
148 The scientific species label has been checked.
149 The photographed individual has a specimen or group ID.
150 The photo is clear enough for its intended task.
151 Photographer, permission, date, and view are recorded.
152 Duplicate and near duplicate images have been reviewed.
153 The image has no answer revealing label or unwanted personal information.
154 Checkpoint: review a contact sheet of each species with your adviser before training.

165 5 Prepare PDFs and plant records
166 5 1 Give PDFs and images different jobs
167 PDFs provide factual knowledge, taxonomic descriptions, and reference material. Verified photographs provide visual recognition examples. A PDF may contain useful plant photos, but each extracted image needs its own correct caption, species label, page reference, and rights check. Illustrations and herbarium scans may differ greatly from phone photos.
168 Preserve the original files. For scanned pages, apply OCR, then manually check scientific names, Arabic letter order, units, and table reading order. Do not assume a successful text extraction means the content is correct.

191 5 3 Build a plant knowledge record
192 For each species, store verified habitat, Oman distribution, synonyms, and source passages. Distinguish an observation in one location from evidence that a plant grows throughout Oman. Record disagreements between references and have your adviser resolve them.
193 Keep these records for retrieval. Do not teach the vision model to infer medicinal properties, conservation status, or geographic distribution from pixels alone. Those facts need documentary support.

196 6 Build JSONL datasets and split them fairly
197 6 1 What JSONL means
198 JSONL stores one complete JSON object per line. It is a container for records, not a training method. Image paths in JSONL must point to actual accessible image files. The loader later opens those files and supplies pixels to the model.
199 Use this schema for your master manifest. Values below are placeholders, not botanical facts. Replace them before training.
200 {
201   "id": "img001",
202   "image": "images/OM001_001.jpg",
203   "species_id": "OM001",
204   "scientific_name": "REPLACE_VERIFIED_NAME",
205   "group_id": "specimen_001",
206   "question": "Suggest the species and describe visible features.",
207   "answer": "REPLACE_WITH_VERIFIED_ANSWER",
208   "source": "REPLACE_REFERENCE",
209   "reviewer": "REPLACE_REVIEWER",
210   "license": "REPLACE_PERMISSION"
211 }
212 
213 Keep the real record on one line. Use UTF 8 so Arabic and scientific names are preserved. Store metadata outside the conversation; do not accidentally include the species label, image filename, or answer in the user prompt.
214 6 2 Write useful answers
215 An answer should identify the supported species when justified and mention visible distinguishing features. Do not describe flowers if the photograph only shows bark. For an insufficient photo, explain what is missing and ask for a closer leaf or flower image.
216 Begin with image plus question examples. Adding text only training to a multimodal pipeline requires loader and collator support; treat that as a later controlled experiment. Use RAG first for detailed document knowledge.
217 6 3 Prevent data leakage
218 A suggested split is 70 percent training, 15 percent validation, and 15 percent test, measured approximately by independent groups. Keep all views of the same individual plant, burst sequence, crop, and augmented copy in one split. Resolve duplicates across sources before splitting.
219 Every supported species should have independent groups represented in all three sets. If there are too few groups, collect more data or reduce scope. Do not solve the problem by placing near duplicates into the test set. GroupShuffleSplit is one documented tool for separating related samples [8].
220 For recognition tests, hold out new individuals of known species. A separate test on entirely new species measures unknown species handling. For factual questions, split related passages before generating questions, so paraphrases do not leak across sets.
221 Checkpoint: save train.jsonl, val.jsonl, and test.jsonl plus the split seed and group membership. Freeze test data.

344 9 2 Define one prediction function
345 Run this on the original model before adding LoRA. The answer is generated without the gold label. The question should be the same for the paired evaluation.
346 def predict(row):
347     FastVisionModel.for_inference(model)
348     messages = [{"role": "user", "content": [
349         {"type": "image"},
350         {"type": "text", "text": row["question"]}
351     ]}]
352     prompt = processor.apply_chat_template(
353         messages, add_generation_prompt=True)
354     inputs = processor(open_photo(row), prompt,
355         add_special_tokens=False,
356         return_tensors="pt").to("cuda")
357     with torch.inference_mode():
358         tokens = model.generate(**inputs,
359             max_new_tokens=180, do_sample=False,
360             use_cache=True)
361     new_tokens = tokens[:, inputs["input_ids"].shape[1]:]
362     return processor.batch_decode(new_tokens,
363         skip_special_tokens=True)[0]
364

366 Use deterministic decoding for paired experiments and record generation settings. This is an evaluation choice rather than a claim that it is always best for the model. For version specific processor changes, follow the corresponding official notebook [3].

409 10 Fine tune with QLoRA
410 10 1 Understand the method
411 LoRA learns small trainable adapter parameters while most pretrained weights remain frozen. QLoRA combines adapter training with a quantized starting model. This reduces memory compared with updating every model weight. An adapter must later be paired with the matching starting model [7].

483 10 Continued Run controlled experiments
484 10 5 Smoke test acceptance
485 A successful smoke test means the model loads, batches contain images, gradients update, loss is finite, and an output can be saved and reloaded. It does not mean recognition is accurate.
486 Inspect a collated batch and a decoded example. Confirm that the user question does not reveal the label and that the answer tokens are not truncated. Check the collator's loss mask against your intended objective. In particular, verify whether the installed configuration trains on assistant responses only or also on user text. Preserve its vision token handling; use the official model specific guidance for masking.
487 If the GPU runs out of memory, stop the failed job and first lower image resolution or sequence length, keep batch size 1, and enable supported gradient checkpointing. If needed, use a smaller model. Increasing accumulation changes effective batch size but cannot fix a single example that is too large.
488 10 6 Start a clean full pilot
489 After the smoke test works, restart from the original checkpoint and add a fresh adapter. Set SMOKE_TEST to False and use a new output directory. Otherwise, your pilot also includes the smoke test updates and its actual training history differs from your report.
490 Train one epoch, evaluate validation answers, then decide whether another controlled run is justified. Change one major setting at a time. Keep a short experiment log rather than repeatedly renting GPUs without a hypothesis.
491 
492 10 7 Diagnose overfitting
493 Training loss can fall while validation recognition gets worse. This suggests the model may be memorizing training examples or exploiting shortcuts. Try fewer epochs, better independent data, or a smaller adapter. Review labels and backgrounds before blaming model size.
494 Checkpoint: one reproducible pilot has saved outputs, validation predictions, and a documented decision. Do not inspect the final test results to select hyperparameters.

534 12 Evaluate the results
535 12 1 Lock the final experiment
536 Select the model and settings using validation only. Then run the original model and selected fine tuned model on exactly the same untouched test images. Use the same questions, preprocessing, and generation settings. Keep a warmup policy and record latency measurement boundaries.
537 A text answer is not automatically a classification label. Define a scoring rule before looking at results. Prefer one canonical scientific name or stable species ID in the output. 555 13 Add document retrieval
556 13 1 Why keep RAG after fine tuning
557 Fine tuning can improve domain behavior and knowledge, but it does not ensure exact recall or accurate page references. Retrieval augmented generation or RAG searches your document collection and gives relevant passages to the model before it answers. This grounds factual explanations in accessible evidence [9].
558 Separate two stages in the app. First, suggest an identity from the photograph. Second, look up facts for the candidate species. If identification is uncertain, present candidate dependent information rather than silently choosing one plant and writing a confident profile.
559 13 2 Build the retrieval collection
560 1. Clean the extracted PDF text and preserve source page information.
561 2. Split it into coherent passages. A starting experiment might use a few hundred words with modest overlap, adjusted to the documents and languages.
562 3. Link passages to canonical species IDs and synonyms where possible.
563 4. Generate embeddings using a model evaluated for your Arabic and English texts.
564 5. Store vectors with text and metadata in a local index such as FAISS or a vector database.
565 6. Combine exact scientific name lookup with semantic retrieval, then inspect retrieved passages.
566 Do not rely only on semantic similarity for nearly identical scientific names. Filter by verified species ID where the identification is established. Keep accepted synonyms in the catalogue.
567 13 3 Answer with evidence
568 Send the question and selected passages with instructions to use only supported facts, identify missing information, and cite source labels. The application should display the actual document and page metadata from retrieved records. Verify that the cited passage supports the claim; a citation's existence does not prove correctness.
569 Photos can support visible shape and color. Your references support habitat, distribution, historical uses, and other background facts. Do not mix these sources of evidence without explaining them to the user.
570 13 4 Understand the cloud boundary
571 If retrieval runs locally but selected passages and photos go to RunPod, those items are processed in the cloud. A local interface does not make the whole system local. Use approved data for the proof of concept. A fully local system needs local model inference, retrieval, embeddings, storage, and any other essential services.
572 Checkpoint: test questions retrieve the correct species' passages and show valid sources, including questions with no answer in the collection.

583 14 Build the application and deploy
584 14 1 Minimal student application
585 Begin with a simple interface rather than a complex mobile application. A Streamlit prototype or a small web frontend with FastAPI is sufficient for the first demonstration.
586 The interface needs photo upload, an optional question, a result, supporting references, and an option to upload another view. Include a clear supported species list. Do not show an unvalidated certainty percentage.
587 14 2 Request flow
588 1. The user uploads a photograph and optional context such as the general region or season.
589 2. Your backend checks file type, dimensions, and size and safely decodes the image.
590 3. The backend sends the image and identification question to the model service.
591 4. It validates and normalizes the returned candidate species.
592 5. Retrieval finds supporting plant records and passages.
593 6. The model or a controlled template creates the explanation.
594 7. The interface shows suggested identity, evidence, uncertainty, and sources.
595 If no reliable candidate is available, ask for a clearer photo of leaves, flowers, fruit, or the whole plant. A failed API request should display a retry message, not a fabricated botanical answer.
596 14 3 API contract to design
597 
598 This is a suggested application contract, not RunPod's built in request schema. Your worker handler and backend must implement it. Validate generated JSON and handle invalid output.
599 14 4 Choose a serving route
600 For a short demonstration, a protected inference service on a Pod can be simpler. For occasional requests, deploy a compatible worker on RunPod Serverless using the saved adapter plus its matching starting model. The worker must accept images and load the correct processor. Confirm adapter and multimodal support in the chosen serving engine.
601 
602 14 Continued Serve through RunPod Serverless
603 14 5 Prepare the worker
604 Package your proven inference code, dependency versions, processor, and adapter. Decide whether the foundation checkpoint is baked into the image, loaded from a volume, or downloaded into a cache. Test the container with a real plant image before connecting the full application.
605 Your handler receives a job, decodes the image, calls the inference function, and returns a JSON result. Loading the model once at worker startup is normally preferable to loading it for every request. Start with one request at a time if your code has not been tested for concurrent GPU use.
606 RunPod Serverless is an optional deployment stage. The introductory guide is at:
607 https://docs.runpod.io/serverless/overview
608 14 6 Protect the API key
609 The student browser should call your backend. Your backend keeps the RunPod API key in an environment variable or secret store and calls RunPod. Do not embed the key in browser JavaScript, a mobile package, a public notebook, or source control.
610 Use the endpoint's documented request format and handle its lifecycle. Queue based endpoints may return a job ID before the result is ready. The backend must poll or use the supported asynchronous flow, enforce timeouts, and handle failures. Do not assume every API request returns an answer immediately.
611 14 7 Configure cost and availability
612 For a prototype, consider zero minimum workers and a low maximum worker count. This can reduce idle compute but the first request may wait for startup and model loading. Workers can bill during initialization and idle waiting, depending on their configuration [10]. Storage and other applicable charges must also be checked.
613 A photo request is larger than a text request. Enforce upload limits and use suitable image resolution. Test retries carefully so the app does not submit duplicate jobs and pay twice.
614 14 8 Demonstrate honestly
615 Show the cloud processing stage during the presentation. If cloud service availability is uncertain, prepare consented example results clearly labelled as prerecorded and keep a live test separate. Never present a saved response as a live prediction.
616 Checkpoint: a laptop application sends a real image, receives the trained model's response, and displays errors cleanly without exposing credentials.

618 15 Move to local hardware
619 15 1 Understand what migration means
620 Moving locally means running the same model and application on equipment under your control. It does not require repeating training. However, the local machine must have enough memory and a compatible runtime. Cloud proof of concept results do not prove equal speed on a smaller machine.
621 If students have no suitable GPU, completing the cloud proof of concept and documenting hardware requirements is a valid project deliverable when approved by their university. Describe local deployment as future work until it has actually been tested.
622 15 2 Transfer the complete package
623 
624 An adapter alone is not a complete model. If you export a merged model instead, test it against the original adapter based setup. Keep the original adapter backup.
625 15 3 Migrate in stages
626 1. Check local RAM, GPU VRAM, storage, drivers, and operating system support.
627 2. Reproduce the cloud inference environment where compatible. Linux or a supported Linux environment can simplify the initial migration.
628 3. Copy or download the exact starting checkpoint and load its matching adapter and processor.
629 4. Run one image directly before starting the API or interface.
630 5. Point the backend's configurable model address to the local service.
631 6. Move retrieval, embeddings, and storage locally too.
632 7. Repeat accuracy, latency, and failure tests on the local hardware.
633 For quantized deployment formats, verify support for the exact VLM architecture, image processor or vision projector, and adapter conversion. A text model export command does not prove image support. Do not assume every VLM can be moved into Ollama unchanged.
